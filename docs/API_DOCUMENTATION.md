# WorkspaceHub API Documentation

Base URL in local Development depends on `launchSettings.json`, for example:

```text
https://localhost:7555
```

All protected endpoints require:

```http
Authorization: Bearer <JWT>
```

## Common Error Response

Handled application exceptions are returned in this format:

```json
{
  "statusCode": 409,
  "message": "Booking is already fully paid."
}
```

Typical status codes:

| Code | Meaning |
|---|---|
| 200 | Successful read/update-style response |
| 201 | Resource created |
| 204 | Successful operation with no body |
| 400 | Bad request / validation error |
| 401 | Not authenticated or authentication failed |
| 403 | Authenticated but not authorized for the endpoint |
| 404 | Resource not found in the current tenant/scope |
| 409 | Business rule or conflict |
| 500 | Unexpected server error |

# 1. Authentication

## POST `/api/Auth/register`

**Auth:** Anonymous

Creates a new tenant and its first Admin user.

The tenant starts inactive and must be approved by a SuperAdmin before the Admin can log in.

### Request

```json
{
  "fullName": "Workspace Owner",
  "email": "owner@example.com",
  "password": "Owner@12345",
  "tenantName": "Example Workspace",
  "tenantSlug": "example-workspace"
}
```

### Response `201`

```json
{
  "tenantId": 13,
  "tenantName": "Example Workspace",
  "adminEmail": "owner@example.com",
  "message": "Registration submitted successfully. Your workspace is pending approval."
}
```

### Rules

- Email must not already exist.
- Tenant slug must be unique among non-deleted tenants.
- `tenantId` is generated by the server.
- Role is not accepted from the request.
- The first user is created as `Admin`.
- Tenant starts inactive.

## POST `/api/Auth/login`

**Auth:** Anonymous

Authenticates a user and returns a JWT.

### Request

```json
{
  "email": "admin@example.com",
  "password": "Password@123"
}
```

### Response `200`

```json
{
  "accessToken": "<jwt>",
  "expiresAt": "2026-09-07T15:00:00Z",
  "fullName": "Workspace Admin",
  "role": "Admin",
  "tenantId": 8
}
```

### Rules

- Inactive users cannot log in.
- Wrong credentials return `401`.
- Locked accounts return `409`.
- Unconfirmed email returns `409`.
- Inactive tenant blocks normal tenant users from login.
- User must have at least one role.

# 2. Tenants

## POST `/api/Tenants/{id}/approve`

**Role:** `SuperAdmin`

Approves a pending tenant and activates it.

### Response

`204 No Content`

### Errors

- `404` tenant not found.
- `409` tenant is already active.

**Role:** `Admin`

Returns the current Admin's tenant.

### Response `200`

```json
{

  "name": "Workspace Tenant",
  "slug": "workspace-tenant",
  "email": "tenant@example.com",
  "phoneNumber": "01000000000",
  "logoUrl": null,
  "address": "Cairo",
  "isActive": true
}
```

**Role:** `Admin`

`204 No Content`

**Roles:** `Admin`, `Staff`

**Role:** `Admin`

```json

  "name": "Main Branch",

  "email": "branch@example.com",
```

**Role:** `Admin`

Updates a branch.

- Branch name is unique per tenant.
- Branch phone and email are not globally unique.
- Another tenant cannot read or update the branch.

# 8. Bookings

## GET `/api/Bookings`

**Roles:** `Admin`, `Staff`

Returns current-tenant bookings with customer and workspace relationships.

## GET `/api/Bookings/{id}`

**Roles:** `Admin`, `Staff`

## POST `/api/Bookings`

**Roles:** `Admin`, `Staff`

### Request

```json
{
  "pricingType": 1,
  "startAt": "2026-09-13T10:00:00Z",
  "endAt": "2026-09-13T13:00:00Z",
  "discount": 30,
  "tax": 10,
  "notes": "First booking",
  "customerId": 9,
  "workspaceId": 31
}
```

### Rules

- Customer and workspace must belong to the current tenant.
- Customer must be active.
- Workspace must be active and available.
- End time must be greater than start time.
- Booking start cannot be in the past.
- Discount and tax cannot be negative.
- Discount cannot exceed the calculated booking amount.
- Unit price is read from workspace pricing and cannot be supplied by the client.
- Non-cancelled bookings cannot overlap for the same workspace.
- Initial status is `Pending`.
- Initial payment status is `Pending`.

### Response

`201 Created`

## PUT `/api/Bookings/{id}`

**Roles:** `Admin`, `Staff`

### Additional payment rule

Once a booking has payments, the following cannot be changed:

- Customer
- Workspace
- Pricing type
- Start/end time
- Discount
- Tax

This prevents historical payment totals from becoming inconsistent with a changed booking amount.

## DELETE `/api/Bookings/{id}`

**Role:** `Admin`

Soft-deletes the booking.

### Booking statuses

| Value | Status |
|---:|---|
| 1 | Pending |
| 2 | Confirmed |
| 3 | CheckedIn |
| 4 | Completed |
| 5 | Cancelled |
| 6 | NoShow |

# 9. Payments

## GET `/api/Payments/booking/{bookingId}`

**Roles:** `Admin`, `Staff`

Returns the payment summary for a booking.

### Response example

```json
{
  "bookingId": 16,
  "totalAmount": 270,
  "totalPaid": 270,
  "totalReceived": 300,
  "remainingAmount": 0,
  "totalOverpayment": 30,
  "paymentStatus": 3,
  "payments": [
    {
      "id": 11,
      "amount": 100,
      "appliedAmount": 100,
      "overpaymentAmount": 0,
      "paymentMethod": 1,
      "paymentDate": "2026-09-05T16:05:22Z",
      "transactionId": null,
      "notes": "First partial payment",
      "bookingId": 16
    },
    {
      "id": 12,
      "amount": 200,
      "appliedAmount": 170,
      "overpaymentAmount": 30,
      "paymentMethod": 1,
      "paymentDate": "2026-09-05T16:07:01Z",
      "transactionId": null,
      "notes": "Overpayment test",
      "bookingId": 16
    }
  ]
}
```

### Meaning

```text
TotalAmount      = booking value
TotalPaid        = sum of AppliedAmount
TotalReceived    = sum of Amount
RemainingAmount  = TotalAmount - TotalPaid
TotalOverpayment = TotalReceived - TotalPaid
```

## POST `/api/Payments`

**Roles:** `Admin`, `Staff`

### Request

```json
{
  "amount": 200,
  "paymentMethod": 1,
  "transactionId": null,
  "notes": "Cash payment",
  "bookingId": 16
}
```

### Payment methods

| Value | Method |
|---:|---|
| 1 | Cash |
| 2 | Visa |
| 3 | Wallet |
| 4 | BankTransfer |

### Rules

- Payment method must be valid.
- Amount must be greater than zero.
- Booking must exist in the current tenant.
- Cancelled bookings cannot receive payments.
- Fully paid bookings cannot receive another payment.
- If received amount exceeds the remaining booking amount, only the remaining amount is applied and the difference becomes overpayment.
- Payment status is recalculated from total applied amount.

### Response

`200 OK` with updated payment summary.

## DELETE `/api/Payments/{id}`

**Role:** `Admin`

Deletes the payment and recalculates the booking payment status.

# Security Notes

- Tenant ID is derived server-side from JWT claims for tenant-scoped business operations.
- Public registration cannot select a role.
- SuperAdmin endpoints require `SuperAdmin` authorization.
- Admin staff creation always creates `Staff` role; role is not client-controlled.
- Identity password and lockout policies are configured centrally.
- JWT issuer, audience, lifetime, and signing key are validated.
- Swagger is enabled only in Development.
- Global exception handling avoids exposing internal stack traces for unexpected `500` responses.
- Secrets should be supplied through User Secrets or production secret/environment configuration, not committed to source control.

# Current Limitations / Future Enhancements

- Already-issued stateless JWTs are not immediately revoked when a user or tenant is deactivated; short-lived access tokens plus refresh/revocation can address this.
- Onboarding is a multi-step workflow and can be hardened with an explicit database transaction.
- Centralized FluentValidation can complement the current service-layer business validation.
- Full refund processing is not yet implemented despite the `Refunded` enum value.
